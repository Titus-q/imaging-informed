# OHIF 影像查看接入规划

OHIF Viewer 是开源的医学影像查看器，跑在浏览器里，提供医院 PACS 工作站级别的阅片能力：
逐层滚动、窗宽窗位调节（肺窗/骨窗/软组织窗）、病灶测量（尺寸、CT 值）、多平面重建（MPR）。

对本项目的意义：报告解读链路解决「**读懂文字**」，影像查看补上「**看见影像**」——
患者拿到 CT 光盘和报告后，能在影像上亲眼确认报告描述的病灶位置和大小。

接入按三档推进，资源需求和隐私风险逐档递增：

## 第一档 · 本地拖拽查看（可立即实施）

用户把 DICOM 文件夹拖进网页，OHIF 在浏览器内直接解析显示，**影像数据不上传、不出本机**。

- 形态：自建 H5 页面（部署 OHIF 静态资源 + local 数据源），不依赖官方 `viewer.ohif.org/local` demo
- 资源需求：纯前端，静态托管即可，零服务器开销
- 隐私风险：极低（数据不出本机，无需额外合规评估）
- 与小程序的关系：微信小程序 web-view 嵌入 H5 需要已备案的业务域名，
  因此正式形态是**独立 H5 页面**；开发阶段可直接在浏览器调试

## 第二档 · 上传 + 云端调阅（等条件成熟）

患者 DICOM 上传至 Orthanc（轻量 DICOM 服务器），OHIF 通过 DICOMweb 协议调阅。

- 解锁能力：
  - **检查历史管理**：多次复查的影像云端留存，随取随看
  - **报告 ↔ 影像联动**：解读页点击「右肺上叶结节」等异常项，跳转到对应序列与层面
- 资源需求：一个 CT 序列可达数百 MB（40G 云盘需要扩容或配清理策略）；
  Orthanc + OHIF + 现有 OCR 服务共存，建议 **4G 内存以上**服务器
- 前置条件：域名 ICP 备案 + HTTPS（DICOM 上传必须走安全通道）
- 隐私风险：中（影像属敏感个人信息，需要访问控制、加密、删除机制、隐私声明）

## 第三档 · AI 辅助分割（远期）

MONAI Label 交互式分割、TotalSegmentator 器官定位覆盖层。

- 资源需求：TotalSegmentator 为 3D 分割大模型，CPU 推理一个序列 30–60 分钟且需 16G+ 内存，
  GPU 是正常用法（按量付费或包月 GPU 实例）
- 合规风险：**高**。「在影像上标注病灶」可能构成辅助诊断功能，触及医疗器械监管红线，
  敏感度比「报告辅助理解」高一个量级，需专业合规评估后才可立项

## 推进顺序

```
第一档（本地拖拽 H5）→ 第二档（域名备案 + 服务器升级 4G 后接 Orthanc）→ 第三档（远期，需 GPU + 合规评估）
```
